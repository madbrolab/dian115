01

部署流程

先把路径与持久化设计正确，再启动容器；这比启动后反复改路径可靠得多。

部署前准备

Docker 环境

Linux 主机、Docker Engine 与 Compose v2。主服务默认 8095，Emby 代理 8098，Navidrome 代理 4534；6060 仅供内网调试。

持久化目录

/config 保存数据库、配置与缓存；使用 AI 工具时持久化 /dian115AI，用于长期记忆与工作文件。更新前优先备份整个 /config。

路径可见性

推荐使用 /media 与 /CloudNAS:shared。dian115、CloudDrive2 与 Emby 对同一媒体的容器路径必须一致或可转换。

先决定路径，后创建规则

整理、STRM、Emby、Navidrome 和文件管理会共同引用路径。部署后再改变映射，容易造成旧规则失效、重复扫描或媒体路径无法匹配。

Docker Compose 部署

Linux、NAS 与 Unraid 优先使用 host 网络；不支持 host 网络或需要反向代理统一入口时，再改用桥接网络。两种写法二选一，不要同时保留 network_mode: host 与 ports。

docker-compose.yml · 推荐 host 网络
services:
  dian115:
    image: madbrolab/dian115
    container_name: dian115
    restart: unless-stopped
    network_mode: host
    volumes:
      - ~/config:/config
      - ~/dian115AI:/dian115AI
      - /var/run/docker.sock:/var/run/docker.sock
      - ~/media:/media
      - ~/CloudNAS:/CloudNAS:shared
host 网络不写 ports

服务直接占用宿主机端口，管理后台通常访问 http://服务器IP:8095。Docker Socket 仅供 DianCupLite 自动更新和镜像管理；不用相关功能可删除该挂载。使用 AI 工具时应保留 /dian115AI 持久化。

docker-compose.yml · 桥接网络 / 反向代理
services:
  dian115:
    image: madbrolab/dian115
    container_name: dian115
    restart: unless-stopped
    ports:
      - "8095:8095"
      - "8098:8098"
      - "4534:4534"
    volumes:
      - ~/config:/config
      - ~/dian115AI:/dian115AI
      - /var/run/docker.sock:/var/run/docker.sock
      - ~/media:/media
      - ~/CloudNAS:/CloudNAS:shared
    environment:
      - PORT=8095
      - TZ=Asia/Shanghai
      # - DIAN115_HTTP_PROXY=http://代理服务器IP:7890
项目默认值用途与注意
主服务8095Web 管理、API 与插件入口；可用 PORT 修改。
Emby 代理8098反向代理与播放重定向；页面改端口后 Compose 映射也要同步。
Navidrome 代理4534不用音乐代理时无需暴露。
调试端口6060pprof / 调试，仅在明确排障时向内网开放。
数据目录/config数据库默认位于 /config/dian115.db，必须持久化。
媒体 / CD2/media、/CloudNAS与 Emby、CD2 的路径保持一致；CloudNAS 挂载保留 :shared。
启动与检查
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail=200 dian115

Docker Socket 是可选能力

它只用于 DianCupLite 读取容器与镜像、检查摘要并执行更新。无需 privileged，也不要把宿主机根目录映射为 /:/host。

路径先固定再建规则

~/media 与 ~/CloudNAS 只是宿主机示例，请改成真实目录；容器内建议继续使用 /media 与 /CloudNAS，减少 Emby、整理和 STRM 的路径替换。

FlareSolverr 过盾工具部署

UIndex 等资源站可能触发 Cloudflare 验证。只有使用这类站点时才需要单独部署 FlareSolverr，然后在“系统设置”的基础设置或代理相关配置中填写服务地址并测试。

docker-compose.yml · FlareSolverr
services:
  flaresolverr:
    image: ghcr.io/flaresolverr/flaresolverr:latest
    container_name: flaresolverr
    restart: unless-stopped
    ports:
      - "8191:8191"
    environment:
      - LOG_LEVEL=info
      - LOG_FILE=none
      - LOG_HTML=false
      - CAPTCHA_SOLVER=none
      - TZ=Asia/Shanghai
    volumes:
      - ./flaresolverr:/config
部署关系dian115 中填写说明
同一个 Compose 桥接网络http://flaresolverr:8191推荐方式，容器名可直接解析。
dian115 使用 host，FlareSolverr 在同一宿主机http://127.0.0.1:8191 或 http://服务器IP:8191只有同机 host 网络才适合使用 127.0.0.1。
分别部署在不同机器http://FlareSolverr机器IP:8191确认防火墙与端口放行，尽量只允许内网访问。
最常见的地址错误

桥接网络中的 127.0.0.1 只指向 dian115 容器自己，并不代表宿主机或 FlareSolverr 容器。首次请求启动浏览器环境可能较慢；8191 不要直接暴露到公网。

首次启动、验收与更新

  1. 打开管理界面访问 http://主机IP:8095。首次使用会要求设置管理员密码，项目没有需要猜测的默认密码。
  2. 完成授权激活如果授权守卫提示激活，按提示填写收到的 License Key。捐赠、邮箱备注和发码核对方式见“捐赠与激活”。
  3. 立即完成安全设置设置强密码；需要外部访问时启用两步验证。OpenAPI Key 只在确实使用 Webhook、Madby 或外部 API 时创建。
  4. 检查容器内路径文件管理应能看到 /CloudNAS 与 /media；看不到时先修正 Compose，不要继续创建整理或 STRM 规则。
  5. 观察日志与运行状态确认容器没有反复重启，数据库位于 /config，端口没有冲突，页面能正常刷新。
最小验收标准

重启容器后管理员密码、激活状态和配置仍在；文件管理能浏览映射目录；仪表板没有持续性的数据库或权限错误。满足这些条件后再进入业务配置。

更新与回滚前应该做什么？
  • 备份宿主机的 config 目录；这里包含主数据库、分库、缓存索引与运行设置。
  • 使用 GitHub AI 工具时，同时备份 dian115AI 工作区内尚未推送的改动。
  • 更新前结束重要整理、分享、秒传、字幕或容器更新任务，避免中途重启。
  • 常规更新使用 docker compose pull 与 docker compose up -d；完成后检查健康状态与最近日志。
02

配置流程

推荐顺序遵循“基础连接 → 资源来源 → 自动化 → 对外服务”，可避免路径和账号反复返工。

推荐配置顺序

  1. 管理员与授权设置管理员密码并完成 License 激活；确认容器重启后密码、激活状态和数据库都能保留。
  2. 115 主账号与目录扫码添加账号，选定活跃主账号，保存安全码，并设置转存、离线、秘享接收及各渠道默认目录。
  3. CloudDrive2填写 CD2 地址、API Token 与容器内挂载根，例如 /CloudNAS；选择主账号实际对应的云盘并执行连接测试。
  4. 判断是否迁移旧 Emby 库已有其它工具生成的媒体库时，先完成下方“Emby 媒体画像 → Madby → FFP”迁移链路，不要立刻大规模生成新 STRM。
  5. 媒体服务与外部接口接入 Emby / Navidrome，按需生成 OpenAPI Key，配置 Webhook、Madby、HTTP 代理和 TMDB 网络。
  6. 下载器与资源来源先让下载器连接成功、保存路径正确，再添加 PT 站点、RSS、Telegram 频道监控和癫影账号。
  7. 订阅、整理与 STRM先用一个小目录测试识别、命名、洗版和多版槽位；STRM 先全量建树，再生成文件，最后开启实时或定时同步。
  8. AI、通知与门户最后配置 AI 提供商、Telegram 通知、门户和卫星服务。它们依赖前面的账号、路径与媒体服务。

旧 Emby 库迁移：先保留画像，再生成 STRM

如果旧 Emby 媒体库由其它工具生成，“Emby 媒体画像”不是普通辅助插件，而是迁移链路的第一步。目标是把旧路径、媒体流信息与 SHA1 画像先匹配和上报，避免新旧条目混在一起。

  1. 完成最小连接先配置管理员、授权、115 主账号、CD2 地址/API Token 与挂载路径。
  2. 只构建目录树在 STRM 规则中先同步目录树，暂时不要生成 STRM，也不要让新 Emby 大规模扫描。
  3. 拉取旧库画像进入“插件中心 → Emby 媒体画像”，填写旧 Emby 地址与 API Key，读取旧库条目、文件路径和媒体流信息。
  4. 配置路径替换把旧 Emby 文件路径映射到 dian115 新的 115 / CD2 目录树，检查匹配率和未匹配记录。
  5. 接入 Madby填写 dian115 地址与 OpenAPI Key；避免原生 Webhook 和 Madby 对同一事件重复通知。
  6. 上报 FFP将可用画像上报到癫影 SHA1 FFP，尽量保留旧库的容器、媒体流、章节与技术字段识别成果。
  7. 最后切换新库确认路径、Madby、FFP 和通知都正常后，再生成新 STRM，并让新的或干净的 Emby 媒体库扫描。
不要同时迁移与大规模扫描

旧路径尚未匹配时就生成新 STRM 并扫描，会把旧库画像、新 STRM 和新 Emby 条目混在一起，后续很难判断重复、缺集与画像归属。

关键配置卡片

系统设置

  • 基础：CD2 地址、挂载路径、系统参数、HTTP 代理。
  • 安全与 API：登录密码、两步验证、OpenAPI Key。
  • 词表：识别替换词、制作组、占位符与分类相关词表。
  • 高级：Webhook、AI 提供商池、背景及外部集成。

账号配置

  • 主账号参与全局 115 客户端、签到、目录和自动切换。
  • 备用 CK 池独立存在，不会自动成为活跃主账号。
  • QPS 限制按账号负载设置；高并发不等于更稳定。
  • 转存、离线与秘享目录用途不同，不建议指向同一临时目录。

媒体路径

  • Emby、dian115 和 CD2 对同一媒体的路径必须可转换。
  • 本地整理仅支持本地到本地；硬链接要求同一文件系统。
  • CD2 整理要求源与目标都在 CD2 挂载根下，操作由 CD2 完成。
  • 混合“本地 → CD2 / CD2 → 本地”不属于整理规则支持范围。

AI 与外部接口

  • AI 支持 OpenAI Chat Completions 或 Responses 协议。
  • 每个使用位置可单独选择提供商和模型。
  • Webhook / Madby 使用 OpenAPI Key，密钥不要放入截图、日志或公开 Wiki。
  • 管理模式 AI 可调用后台工具，应保留危险操作确认。

上线前检查

检查项通过标准失败时优先检查
CD2连接测试成功，能浏览正确云盘目录地址、挂载根、容器路径、云盘名称
115 账号Cookie 有效，账号检查正常，目录 CID 已确认设备类型、扫码状态、验证码、QPS 与风控
TMDB探索页能显示元数据与海报代理、语言、网络与缓存
Emby库统计可读取，代理播放链路正常地址、API Key、路径转换、ItemID 同步
PT站点可搜索，下载器能添加测试任务站点认证、代理、保存路径、客户端标签

验证时从小范围开始

订阅、整理、自动分享、刷流和容器更新都具备批量能力。第一次配置请只使用一个站点、一个小目录或一部媒体验证，确认日志与目标结果后再扩大范围。

03

部分功能导览

按用户任务解释常用能力与边界；这里只选取重点功能，不代表 dian115 只有这些功能。

常用能力持续扩展

dian115 还包含追剧日历、下载管理、任务队列、运行日志、网络测试、路径与缓存维护等能力，可按实际使用场景逐步配置。

01

仪表板

一眼判断系统是否健康、任务是否堆积、媒体链路是否工作。

入口：总览

仪表板把“文件、资源、连接、任务、下载与播放”放在同一屏。它不是只看数字的装饰页，而是日常排障的第一站。

趋势与资源查看 STRM、软连接新增趋势，以及 CPU、系统内存和 dian115 自身内存占用。
连接与账号集中确认 CD2、115、Emby、Navidrome 与监控模式，并查看网盘容量和账号数量。
任务与播放显示全局任务队列、下载速度、302 播放统计、播放排行与当前播放会话。
建议的巡检顺序

先看系统连接状态，再看任务失败数，最后检查日志。CPU 短时升高不一定是故障；持续高占用同时伴随队列不前进才值得重点排查。

02

探索发现

把媒体元数据、PT、磁力、癫影和 TG 频道资源统一到一个发现入口。

入口：探索发现

“探索”负责从媒体角度找内容，“资源页签”负责从下载来源角度找文件。先选中媒体再订阅，或直接在对应来源中搜索，二者服务于不同场景。

探索 / TMDB

按电影、剧集、热度、上映时间、评分、类型、语言、年份和地区筛选；卡片会显示评分、媒体类型与是否已拥有，适合从“想看什么”出发。

PT

汇集已启用站点的最新种子与搜索结果。可结合站点、促销、大小、做种数和质量条件筛选；下载前仍需正确配置站点与下载器。

癫影

通过已配置的癫影 OpenAPI 账号检索平台资源；在聚合订阅中可作为资源来源之一。签到、上传分享和账号能力在“癫影”插件内管理。

TG 频道

展示 Telegram 频道监控插件采集并解析的 115 分享。频道需要先完成 TG 登录、监控目标与转存策略配置，缓存用于去重和状态追踪。

磁力来源怎么理解

海盗湾、UIndex、TGx 与 TheRARBG 是独立的公开索引页签，适合“已知道关键字，直接找磁力”的场景。资源进入 115 离线前会经过链接解析、去重与离线任务处理；请自行确认资源版权与所在地法律要求。

来源隔离各索引的可用性、字段和排序不完全相同，某一页签异常不代表其他来源不可用。
结果去重离线链接缓存减少同一磁力或 ED2K 的重复解析与重复提交。
落地位置最终目录由活跃 115 账号的离线目录或对应渠道默认目录决定。
03

订阅

从“想要某部媒体”开始，自动搜索、筛选、下载与后处理。

入口：媒体订阅

订阅支持电影、剧集和精准演员订阅。每条订阅背后是一个持续评估的意图：系统根据来源策略找候选，按质量方案筛选，成功后交给下载器或聚合资源链路。

电影 / 剧集按 TMDB 身份持续追踪；剧集理解季与集的覆盖情况，避免只根据标题粗略判断。
演员订阅先从 TMDB 确认演员身份，再按媒体类型、年份等规则扫描作品；可暂停、重评估并查看每项排除原因。
来源组合可使用癫影、PT、TG 资源或聚合策略。入口行为可设为固定模式，也可每次询问。
一条订阅如何执行
创建意图媒体 / 季 / 演员
检索来源癫影 / PT / TG
过滤排序质量、体积、促销
执行落地转存或下载器
后处理秒传、整理、通知
  • 全局质量方案由电影与剧集分别维护，订阅只引用方案，避免每条订阅复制一套复杂规则。
  • PT 支持周期自动搜索与独立 RSS 反向匹配；关闭自动搜索不会阻止手动搜索。
  • 候选可按自定义优先级逐层比较，跨站同质量候选可保留为失败换源。
  • PT 下载完成后可对选中的视频/字幕秒传到 115；失败后可选择普通上传或 CD2 投递。
“PT 成功”与“115 后处理成功”是两件事

PT 成功表示任务已添加并完成文件选择。后续秒传或 CD2 投递是独立任务，失败不会把已经完成的 PT 下载标记为失败，也不会自动停止做种。

04

媒体整理

识别、分类、命名与版本决策的完整流水线。

入口：媒体整理

整理不是简单移动文件。它会先判断规则与路径模式，再识别媒体身份、读取技术字段、应用分类和命名，最后根据重复策略决定跳过、覆盖或保留多个版本。

文件整理

  • 本地模式：源和目标均为本地路径，支持移动与硬链接；硬链接要求同一文件系统。
  • CD2 模式：源与目标都位于 CD2 挂载根下，通过 CD2 操作，传输方式为移动。
  • 支持文件扩展名、最小体积、排除目录/关键词、字幕联动、失败目录与自动监控。

识别链路

  • 全局词表与 GuessIt 3.8.0 先提取标题、年份、季集和技术字段。
  • TMDB 用标题和路径证据确认媒体身份，并返回海报与规范名称。
  • 可在“无标题”“TMDB 未命中”或“始终”三种时机调用 AI 二次识别。
  • ffprobe 读取真实媒体流信息，辅助命名、评分与洗版。

评分洗版与多版共存

策略分组可选策略适用场景
单一版本跳过、按大小比较、评分洗版媒体库中每个电影或剧集只保留一个目标版本。
多版共存全部保留、多版本洗版同一媒体保留多个版本；可用规则级槽位管理不同版本类型。
  • 评分洗版：新旧文件使用同一套全局评分规则比较；只有新版本胜出时才执行替换，历史页会记录结果与原因。
  • 多版共存：为 4K、杜比视界、HDR、1080P 等需求设计独立槽位；版本目录和别名由全局配置统一控制。
  • 多版本洗版：只在同一槽位内竞争，不会用一个版本误删另一个目标槽位；被淘汰文件是否删除由规则明确控制。
  • 前置过滤：识别完成后立即判断不需要的版本，避免无效文件进入后续命名与比较。
洗版前先关闭自动删除

第一次调规则时，先保留被过滤或被淘汰的源文件，使用“识别测试”和小样本历史确认分数、槽位与命名都正确，再考虑开启删除。

全局缓存与 FFP 缓存

减少重复外部请求，同时让同一 SHA1 的媒体信息跨功能复用。

入口：全局缓存
缓存保存内容主要价值
TMDB媒体元数据与海报索引加快探索、订阅与识别，减少重复请求。
115 分享分享码、质量与有效性避免反复解析相同分享，跟踪失效状态。
TG 监控分享频道采集的分享链接频道去重、资源状态和订阅复用。
离线链接磁力与 ED2K 记录避免重复提交与重复解析。
FFP-cache以 SHA1 索引的容器、媒体流、章节与技术字段整理、洗版、ED2K、媒体画像与远端上报复用。

FFP-cache 的工作方式

  • 来源区分为本地上报、FFP 探测缓存与 Madby 读取缓存，可按来源筛选。
  • 读取采用本地优先；远端命中会写回本地，后续同一 SHA1 可直接复用。
  • 低完整度信息不会覆盖高完整度信息；页面显示命中次数、冲突次数与上报状态。
  • 批量整理可预取 FFP 缓存，减少每个候选都单独执行 ffprobe 的成本。
  • 删除缓存不会删除真实媒体；后续读取仍可重新探测，但待上传队列中的对应项会同步清理。
缓存不是数据源

当媒体路径、站点认证或分享内容已发生变化时，应刷新或清理对应缓存再验证。不要用“清空全部缓存”代替对错误配置的排查。

选择 CD2 路径时必须与“账号配置 → 扩展设置”中的主账号云盘一致。云盘名称或路径错配会导致音乐条目无法映射到 115 文件。

AI 助手

既能解释系统状态，也能在授权范围内调用 dian115 管理工具。

入口：点点 → AI 助手

AI 助手是综合助手的一部分，与“会话助手”和“音乐”共享浮动入口。AI 模式支持流式回复、推理过程、工具进度、Markdown、回复复制、停止生成、新会话与本地历史。

管理模式可读取系统状态并调用账号、订阅、任务、PT、整理、后台 API 等原生工具；危险动作需要明确确认。
闲聊模式不以系统管理为首要目标，适合解释概念、整理思路和普通问答，减少不必要的工具调用。
TG 助手网页助手与 Telegram 助手共用数据库中的提供商池，可按使用位置选择不同模型与允许工具。
模型与提供商配置
  • 只支持 OpenAI 兼容协议，可在 Chat Completions 与 Responses 中二选一。
  • 支持多个提供商、模型列表、上下文上限、温度、Top P、Tool Choice、并行工具调用和请求超时。
  • 网页助手、TG 助手、媒体整理和 AI 字幕可分别指定 provider / model。
  • 上下文达到限制后会按完整对话轮次整理旧消息，避免切断工具调用链。
GitHub 与仓库工具

配置 Fine-grained PAT 后，AI 可在 /dian115AI 工作区拉取、检查、修改、暂存、提交和推送仓库，也可访问 GitHub 的 Issue、PR、Release 与 Actions。Token 仅提交给后端加密保存，不应回填到 AI 上下文、Git URL、命令参数或日志。

管理模式具备真实操作能力

使用工具调用稳定的高阶模型，并把 Tool Choice 保持为 auto。不要要求 AI 输出 Cookie、Token、密码、安全码或 API Key；后台工具会对敏感字段脱敏，并排除登录、凭据、上传下载流、系统重启等高风险通用接口。
