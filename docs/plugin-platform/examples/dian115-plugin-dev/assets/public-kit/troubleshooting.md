# 插件排错

先在插件中心打开“错误诊断”，再结合运行状态和插件日志排查。记录宿主版本、插件 ID/版本、操作时间、动作或任务 ID，以及错误码、diagnostic_id。分享日志前检查并删除私人业务内容；不需要提供宿主数据库或密钥。

诊断面板展示启动、运行退出、调用协议、执行和结果保存等阶段，以及可关联的 job_ref、invocation_id。错误响应、任务结果和运行状态中的 diagnostic_id 可定位同一条诊断；详细内容只向管理员开放。宿主对凭据类字段脱敏、截断详细文本，复用有界安装日志，最多展示最近 20 条结构化错误；这不是永久审计档案。用量读取失败时不显示配额数字，不把失败当作零用量。

同一 invocation_id 的终态失败回执保留原错误码、HTTP 状态和可用的 diagnostic_id，读取回执不会重新执行或重复记录同一错误。诊断不可用时按调用 ID 查安装日志；错误详情仍由管理员查看，失败回执仅保存安全错误码和诊断编号。

## 页面打开与恢复

| 表现 | 含义与处理 |
| --- | --- |
| 空闲，按需启动 | 普通插件当前没有驻留模块。打开页面读取状态会唤醒它；空闲不表示故障。 |
| 启动中 | 同一安装的首次请求共用一次加载。等待当前启动完成，避免连续点击重启。 |
| 崩溃恢复中 / runtime_backoff | 宿主正在退避重试。查看最后一次错误；频繁手动重启会打断恢复和诊断。 |
| runtime_resource_limit | 加载数量、常驻数量或声明内存预算不足。先减少常驻/释放空闲插件，不要连续重启；这不消耗崩溃预算。 |
| runtime_failed | 自动重启预算已用完。先定位原因，再更新包或手动重启；暂时故障冷却后可重新获得预算。 |
| runtime_package_invalid | 包入口、WASM 编译、ABI 或初始化不符合要求。发布者修复并重新打包；仅刷新页面不能修好无效包。 |
| 页面资源或渲染失败 | 检查 Federation 入口、签名资源、singleton 依赖和主题契约。它与后端状态读取失败分别显示。 |

后端失败期间页面仍可显示错误和恢复操作。使用“重新读取状态”再次请求；包级永久错误需要修包。不要把“卸载后重装”当成保留配置的重启：卸载会清空数据。

## 动作和 Host Call

| 错误 | 处理 |
| --- | --- |
| invocation_queue_full | 接纳门限已满。减少页面并发和轮询，稍后重试同一次业务。 |
| invocation_queue_timeout | 本次在等待阶段超时，没有进入 guest 执行。 |
| invocation_cancelled | 等待执行时调用方取消。已进入执行的动作由宿主预算管理。 |
| runtime_timeout | 执行期限耗尽，模块会被关闭。先查询业务结果或回执，确认副作用后再决定是否重试。长流程改用宿主任务和有界批次。 |
| runtime_protocol_error | 对照 WASM 协议检查 state 版本/ETag、action/job 枚举及 JSON 大小。 |
| HTTP 404 / 412 / 413 | Storage 404 表示键不存在；412 表示版本冲突，应读新值后合并；413 表示超过配额。 |

Host Call 传输成功时，目标 HTTP 仍可能是 4xx/5xx。使用 SDK 的 `CheckResponse` 或 Storage helper 检查状态、Problem 和 retryable，不能只判断 Go error。同一次重试必须使用相同请求和稳定幂等键；新业务使用新键。上游超时不等于没有完成，不得自动重复非幂等操作。

## 后台任务和存储列表

长任务可在主项目任务队列查看进度、结果和诊断编号，也可用原 job_ref 查询。队列取消是协作中断，不能撤销已经完成的外部副作用；attention_required/submission_uncertain 应先核对真实上游结果。卸载会清除队列中的插件记录，重启后以持久 Host Job 状态为准。

Storage 分页仅返回元数据，看到空 items 不等于值读取失败。确认 prefix 大小写和字面字符；每页 limit 为 1–100，跟随 next_cursor。400 invalid_cursor 应从第一页重新开始，不自行解码或修改游标。配额比较的是已提交 JSON 值字节数，包含受管页面偏好，不等于数据库文件大小。详见 [存储分页与用量](storage-and-lifecycle.md#分页与用量)。

## 常驻、资源与文件

新插件优先使用宿主调度、watch、Telegram 声明路由和事件，默认不要常驻。resident 模式有第二个独立模块实例，两份内存不共享；两个实例分别初始化，resident 循环返回或报错会触发恢复。

WASM 文件不超过 2 MiB。使用受支持的 TinyGo 构建，不链接 Go 标准运行时或 `encoding/json`；示例使用轻量 `pluginjson`。模块内存上限与宿主进程 RSS 是不同指标，不能把 manifest 的 memory_mb 当作整个进程占用。

包内资源只读路径为 `/package`，适合固定模板，不能保存业务数据。配置通过 Host Storage 保存。不要硬编码 `/config`、访问宿主数据库或依赖不存在的可写 `/data` 挂载。

## 卸载清理失败

卸载会先停用安装、停止运行和取消宿主任务，然后清理数据库记录、私有文件、暂存包和专属编译缓存。任何步骤失败都会返回错误并保留“正在清理”的停用记录，全部完成前不报告成功。

先修正错误中指出的存储或文件系统问题，再重试卸载。宿主启动也会继续处理清理标记。不要手工修改安装 ID、把外部目录改成插件路径，或开启旧安装以绕过清理。卸载后重新安装从空配置开始；升级、停用和重启则保留持久配置。

## 发布前检查

依次运行 [示例构建和公开检查工具](conformance/README.md)，再在宿主中验证真实模块的首次打开、保存配置、动作、休眠唤醒、失败恢复和卸载重装。静态检查通过只代表所列契约通过，不能代替真实 HTTP 返回和业务结果验收。

协议细节见 [WASM runtime](wasm-runtime-v1.md)、[Host Call](host-call-v2.md) 和 [存储与生命周期](storage-and-lifecycle.md)。


若旧页面出现 localStorage、IndexedDB 或直接 fetch 被拒绝，按 [UI 隔离迁移](ui-isolation-v1.md) 改用 api.storage 和 Host Call；不能以取消 sandbox 解决。后台任务先查 job_ref；支持恢复回调的任务会先只读核对再续跑，recovery_verification_required 表示结果仍需人工核实，recovery_package_changed 表示当前包不能解释原检查点。


页面渲染或异步异常可在 frame 内“重试插件页面”，也可按诊断编号查记录并导出脱敏诊断。刷新信号在线时不持续轮询 state；隐藏页面断开订阅，返回页面会重新读取。长任务恢复方法及预算见 [可恢复任务](job-recovery-v1.md)。
