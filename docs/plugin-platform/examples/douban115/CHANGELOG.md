# 变更日志

本项目版本号在 1.0.0 处重置：1.0.0 之前的版本（1.4.x）为内部迭代版本，1.0.0 起为对外正式版本，之后按 SemVer 正常迭代。

## 1.0.8（2026-09-28）

### 修复

- **同步任务跑久了插件就整体崩溃重启**。
  - 排查过程（真机取证）：给运行时加了内存与心跳探针后在真机复测，堆占用只有 1–3 MiB（`sys` 8 MiB、GC 次数个位数），**不是** 256 MiB 线性内存超限；任务执行期间从外部高频调用前台 action 也全部在 0.2–0.7 秒内返回，**不是** 常驻任务把前台调用堵死。真正的形态是：一次同步被当成一次连续计算在跑（榜单同步实测 60–150 秒、Emby 同步可达数百次外网请求），宿主侧的活性探测与排队调用长时间得不到响应，累积失败后监督器按 `restart_policy: on-failure` 回收整个模块——日志里表现为「常驻同步调度已启动」反复出现，最后一轮任务的进度全部丢失。
  - **同步任务改为分片执行**（`runtime/jobslice.go`、`runtime/jobsteps.go`）：榜单、想看、Emby 三类同步统一拆成小片，每片只做 5 秒之内的工作，片与片之间主动 `time.Sleep` 让出控制权；每片结束把进度写进 Host Storage（`job_state`），被回收后下一轮调度**从断点继续**，而不是从头重来（常驻循环在有未完成任务的空档会把轮询间隔从 30 秒降到 2 秒）。
  - **同类任务互斥**：已有任务在跑时，「立即运行」请求继续排队、cron 到点也不重入，避免两个同步互相打断。
  - 界面状态栏实时显示分片进度（如「榜单订阅（2/6：全球口碑）第 3/10 条…」）。
- **Emby 同步是最容易失控的一环，一并收敛**：
  - 它一次「已观看」查询就是 100 部电影 + 200 集剧集，每条未同步条目还要走 TMDB 详情 + 豆瓣搜索 + 豆瓣标记（2~3 次外网请求），首次同步可达几十分钟；而且它**不打任何日志**，崩溃时现场全无。现在按片推进，并补充关键日志（播放记录条数、每用户完成情况）。
  - **每轮最多实际标记 40 条**（`embyMaxPerRun`），剩下的下一轮继续；每标记一条就落盘，不会重复请求。
  - **修掉「永远同步不完」**：已同步记录超过 600 条时会按 map 随机删除，被删掉的条目下一轮又被重新同步一遍——于是每 30 分钟一轮的 Emby 同步永远做不完、任务时长无限累加。上限提高到 4000（超实际规模），正常规模下不再触发裁剪。
  - 想看同步同样按页分片：一次只抓一页（15 条），不再一次抓完所有用户的所有页。
  - **连续失败熔断**：连续 8 条未能同步就提前收工并报明原因。Emby 地址不可达或豆瓣 Cookie 失效时，每条都要等一次网络超时，几百条就是几十分钟空转——这正是真机上「Emby 同步跑不完」的直接原因（实测该环境的 Emby 地址 `127.0.0.1:8096` 在 dian115 容器内不可达，宿主的 broker 返回 HTTP 500，旧版会为几百条条目逐条等超时）。
- **Emby 用户配置填登录名也能用**：配置里的 `emby_user_id` 常被填成 Emby 的登录名而不是用户 ID，直接拿去拼接口会 500。现在先查一次用户列表按 ID 或名称匹配，匹配不到再按原样使用。
- **修复想看同步结果里同一用户被重复列出**（昵称只在首页解析得到，之前每一页都记一次）。
- **修复「立即运行」的队列标记清不掉、同一个任务被连着跑好几轮**：清队列那一步写 Host Storage 时可能撞上乐观并发冲突而没写成功，残留的标记会让下一轮调度再跑一遍同一个任务。现在任务收尾时会再清一次标记，重新入队前也会先看队列里是否已有同类请求。
- **前台 action 加超时保护**：`preview-ranks` 单次最多预览 2 个榜单（拉一个榜单 RSS 就要几秒，多榜单必然撞上前台预算），剩余榜单在结果里提示分批查看。

### 说明

- 测试台断言增至 **149 项**：新增检验 L，覆盖「长任务被拆成多片、片与片之间确有让出空隙（实测 host.call 最大间隔 753ms）」「任务完成后 `job_state` 清空、队列标记清除」「注入一个半成品 `job_state` 后能从断点续跑」。

## 1.0.7（2026-09-28）

### 回退

- **整体移除 1.0.6 接入的 dian115 内部识别引擎**（`POST /api/organize/test-recognize`），媒体识别回到 1.0.5 的路径：本地 TMDB 搜索（含标题变体）→ 豆瓣原名/又名兜底。原因：该接口不在插件标准可调用目录内，且当前宿主（4.0.55）不支持 `permissions.host_access` 扩展访问声明，宿主识别始终处于「探测一次即停用」的状态——功能上等于没有，却在设置页多出一个用不上的开关和一条常驻的「宿主未开放内部识别能力」提示。等上游支持后（见 madbrolab/dian115 issue #5）再重新接入。
  - 删除 `runtime/host_recognize.go`、`use_host_recognize` 配置项与设置页开关、state 的 `hostRecognizeOff` 字段；识别策略版本号回落为 **v4**（1.0.6 写下的 v5 缓存自动作废，按 1.0.5 策略重识别一次，结果一致）。

### 修复

- **插件页面底部出现大片空白**。根因在宿主的插件沙箱桥接（插件侧只能规避）：
  - 桥接把 iframe 高度取为 `max(body.scrollHeight, documentElement.scrollHeight, …)`，而宿主基线 CSS 给 `html/body/#plugin-sandbox-root` 都设了 `min-height: 100%`，且根元素的 `scrollHeight` 永远不小于视口（= iframe 当前高度）——三者叠加使 iframe 高度**只增不减**：内容一旦从高变矮（收起折叠、从设置页切回仪表盘），底部就固化出大片空白。
  - 修复：① 检测到沙箱 iframe 时给根元素加 `douban115-sandbox` class，用全局样式清掉 `min-height: 100%`，让 `body.scrollHeight` 回到真实内容高度；② 内容尺寸变化（ResizeObserver / iframe resize）时按宿主的 `resize` postMessage 协议**主动上报组件根的真实高度**（channel 取自 iframe URL hash），上报后短促补发两次，确保压过桥接自身「不低于当前视口」的旧值。本地预览（不在 iframe 里）自动跳过。

### 说明

- 测试台断言 **140 项**：检验 J/K 恢复为验证「标题变体 + 豆瓣原名兜底」，删除宿主识别专属的检验 L/M 与 `/api/organize/test-recognize` mock。

## 1.0.6（2026-09-28）

### 新增

- **媒体识别改为调用 dian115 内部的识别引擎**（`POST /api/organize/test-recognize`）。榜单与「想看」条目不再只依赖插件自己那套「标题 → 标题变体 → 豆瓣原名」的逐层补丁，而是先把条目交给宿主自己的识别引擎：它与 dian115 的整理、刮削是同一套识别逻辑与同一份多语言别名库，**识别结果与宿主完全一致**（用户在宿主里认得的条目，插件里也认得）。
  - 引擎只接受「像文件名」的输入（实测 `流人 S06 2022` → 《流人》95480，而 `流人 第六季` 因中文季号解析不出来、`流人 S06` 因缺年份都不查 TMDB），因此插件负责把榜单标题整理成引擎认得的形态：剥掉标题末尾的季号与年份、中文季号（「第六季」）换算成 `S06`、补上条目的年份，再交给引擎。
  - **优先但不独占**：引擎给出结论就用它的 `tmdb_id` 与海报；未命中、类型与榜单不符、宿主没有该接口、权限未批、或用户在设置页关掉开关时，全部自动回落到原有识别路径，不会比 1.0.5 更差。
  - 引擎返回的类型与榜单类型不一致时**不采用**并回落（宁缺毋错）：类型错了后续订阅会跟着错。
  - 识别结果同样进 `tmdb_cache`，第二轮同步不会再调用引擎；豆瓣原名兜底触发的「重搜」不会再调一次引擎（引擎拿到的输入与条目本身相同，只是换搜索词）。
- 设置页新增「媒体识别」开关（`use_host_recognize`，默认开启），可对比宿主识别与插件自有识别的效果。
- **新增 `permissions.host_access: "extended"`**：该识别接口不在插件标准可调用目录内，扩展访问下才可调用，安装/升级时宿主会作为**高风险权限**单独征求确认。扩展调用只用到这一个接口（已在 `permissions.apis` 中逐条披露用途）。

  > **注意（2026-09-28 实测）**：dian115 **4.0.55**（当前最新版，自动更新显示已是最新镜像）尚不支持该权限字段——带上它的包会被宿主拒绝解析（`unknown field "host_access"`），且该版本的插件可调用目录（164 条）里也没有识别接口。因此本版本**未声明 `host_access`**，宿主识别在这类宿主上不会生效：插件会在第一次调用被拒后**自动停用**（记 `host_recognize_off` 标记，不再重复请求、不刷日志），识别全部回落到插件自带匹配，效果与 1.0.5 一致。等宿主支持扩展访问后，声明该权限即可启用（届时无需改动识别逻辑）。

### 变更

- 识别策略版本号升至 **v5**，旧的「未识别」缓存整体作废，存量条目按新策略（宿主识别优先）重新识别一次。

### 说明

- 测试台断言增至 **154 项**：检验 J 新增「条目先交给宿主识别引擎、入参为 `流人 S06 2026`、带幂等键、命中后不再走豆瓣原名」；检验 K 用同一部剧的另一个豆瓣条目（《驽马 第六季》）验证「引擎未命中 → 回落插件自有识别 → 豆瓣原名兜底」；检验 L 覆盖开关关闭后完全不调用宿主识别；检验 M 覆盖「宿主未开放该接口时只探测一次就自动停用、识别结果不变、界面能看到原因、保存配置后重新探测」。

## 1.0.5（2026-09-28）

### 回退

- **回退豆瓣榜单封面**，榜单封面重新全部取自 TMDB（**撤销 1.1.0 的改动**）。豆瓣图床对海报路径做 referer 白名单校验，封面只能由运行时取回再以 data URL 交给界面，链路长、往返多；本次把这条链路整体移除：`runtime/cover.go`、`rank-covers` 动作、快照的 `cover_key` 字段、RSS 封面解析、manifest 里的 `https://img9.doubanio.com` 网络权限、前端的分批取图逻辑全部删除。榜单卡片恢复为直接用 TMDB 海报地址。

### 修复

- **TMDB 没有中文标题的条目永远识别不出来**（如《流人 第六季》「TMDB 未匹配」）。这类条目的共同点是：豆瓣给的是中文译名，而 TMDB 只有原名——TMDB 里这部剧就叫 Slow Horses，中文本地化名就是英文原名，搜「流人」只会返回标题里恰好含「流人」二字的无关条目（《潮流合伙人》《千古风流人物》），识别逻辑为避免张冠李戴把它们全部拒收，结果是永远没有封面。
  现在按标题识别失败时，会去豆瓣条目接口取该条目的**原名与又名**，用它们重搜一次 TMDB：
  - 数据源为豆瓣移动端接口 `https://m.douban.com/rexxar/api/v2/{tv|movie}/{id}`，返回 `original_title`（「Slow Horses Season 6」）与 `aka`（「翻盘特工队(港)」「驸马」「慢马」…）；类型不符时豆瓣返回 301，按响应体里的真实地址纠正后重试一次。
  - 原名优先，又名次之；又名里的「(港)/(台)」括号注释会先清掉（对 TMDB 搜索无帮助）；与榜单标题同源的名字跳过（那个词已经搜过并且失败了），单个条目最多试 6 个名字。
  - **代价受控**：只有标题彻底搜不上的条目才会去豆瓣取一次原名，结果（含「取过但没有」的负结果）缓存到 `douban_alias`；兜底命中的结果会同时写回「榜单标题」对应的 TMDB 缓存键，因此同一部剧下一轮同步直接命中，连原名缓存都不必再读。
  - 识别策略版本号升至 **v4**，旧的「未识别」缓存整体作废，存量条目会按新策略重新识别一次。

### 说明

- 测试台断言 137 项：检验 J 的《流人 第六季》从「必须判为未识别」改为「靠豆瓣原名识别为 Slow Horses 并订阅」；检验 K 改为覆盖豆瓣封面机制已整体移除（无封面缓存、`rank-covers` 动作不存在）、原名只在识别失败时才取、301 纠正、缓存与「下一轮不再读原名缓存」。

## 1.1.0（2026-09-28，已撤回）

> **本版本已由 1.0.5 回退**，请勿使用。豆瓣榜单改用豆瓣封面图的方案链路太长（豆瓣图床 referer 白名单 → 必须由运行时取图 → 再以 data URL 经宿主 Broker 交给界面），实际体验不如直接使用 TMDB 封面。

### 新增

- **豆瓣榜单改用豆瓣自己的封面图**：榜单快照里的封面不再一律取自 TMDB，而是按榜单来源区分——豆瓣榜单（即将上映 / 实时热门 / 华语口碑 / 全球口碑 / 电影口碑）直接用豆瓣条目自己的海报，**BangumiTV 榜单继续用 TMDB 封面**（bgm.tv 的条目在豆瓣上没有对应）。豆瓣封面与榜单条目一一对应，不存在 TMDB 模糊搜索带来的张冠李戴风险。
- **封面在榜单同步时预取并缓存**（Host Storage，键为 `cover_<榜单>`），界面打开即显示，不额外等待；缓存按展示范围（每榜前 5 名）维护，随榜单换血自动清理，命中缓存后不会重复取图。**按榜单分键存放**是必要的：宿主存储读取约 30ms/KB，若所有封面挤在一个键里，界面每次取图都要把全部封面（数百 KB）搬一遍。
- 测试台断言增至 **139 项**（新增检验 K 覆盖封面来源分流、回落、归一化、referer、按榜单缓存与格式版本作废）。

### 说明

- 豆瓣图床对海报路径做 **referer 白名单校验**：Referer 属于 `*.douban.com` / `*.doubanio.com` 才返回 200，其他站点（包括 dian115 自己的 origin）返回 403，空 Referer 返回 418。浏览器既不能伪造 Referer（`fetch` 的 `referrer` 选项对跨域目标会被丢弃），也无法让 `<img>` 带上豆瓣域名，因此封面必须由运行时带 Referer 取回，再以 data URL 交给界面。为此新增 `rank-covers` 动作，并在 manifest 中声明 `https://img9.doubanio.com`（GET）网络权限。
- 取图地址统一归一化为固定图床分片 + `thumb` 小图（约 113×170，平均 4.5KB）：同一张图在 img1~img9 之间互为镜像，固定分片后只需声明一个 origin；小图则让 `rank-covers` 的响应远低于宿主对 action 结果的 256 KiB 限制。列表卡片只有 34×50（历史列表 40×58），`thumb` 已够 2~3 倍屏显示，而 RSS 默认给的 `m_ratio`（540×810，40~110KB）大了近 10 倍——封面要经宿主 Broker 传输、按 KB 计费，尺寸直接决定界面出图速度，因此做了尺寸降级。缓存带格式版本号，换尺寸/编码后旧缓存自动作废。
- 个别榜单的 RSS 不带封面（「即将上映」只给简介），此时回落到豆瓣条目页取封面；条目页也取不到时保持 TMDB 封面。

## 1.0.4（2026-09-28）

### 修复

- **封面与名称对不上（张冠李戴）**：例如《流人 第六季》的封面是《潮流合伙人》、《罗斯》的封面是《普罗米修斯》。原因是 TMDB 的中文搜索是模糊匹配（搜「流人」会把《潮流合伙人》《千古风流人物》排在第一页），而旧打分只要媒体类型对得上就取分最高的一条，且 **热度分（`vote_count/500`）没有上限**——一部高票老片能盖过标题完全吻合的新片。现在打分改为：名称相关性分档（完全相等 / 前缀 / 包含 / 二元组相似度）＋年份加分＋**封顶的热度分**，并设最低接受阈值（`tmdbMinAccept`）。低于阈值说明只是「碰巧含有相同字词」的无关条目，直接判为**未匹配**（宁可不显示封面，也不错配）；状态标签相应改为「TMDB 未匹配」。
- **归一化丢字导致日文标题无法比对**：`normalizeTitle` 此前用「码点 ≥ 0x3400」判断保留字符，会把全部日文假名（U+3040–U+30FF）和韩文谚文丢掉——「ヤニねこ」这类纯假名标题会被归一化成空串，名称比较无从进行，只能退回按热度选片。现改用 `unicode.IsLetter/IsDigit`。
- **用 TMDB 原名（`original_name`/`original_title`）参与匹配**：BangumiTV 等榜单给的是日文原名，而 TMDB 的本地化标题是中文意译（`ヤニねこ` → `尼古喵喵`），只比本地化标题会漏识别。现在本地化名与原名一起比较，取相关性最高者。这一项同时让此前一批「有封面但显示不出来」的日文条目恢复正常识别。
- **历史里的旧错配会随历史一直沿用**：榜单/想看历史中已订阅的条目此前会直接沿用历史里的 TMDB 关联，即使它在旧版策略里配错了也不会纠正（真机上《流人 第六季》因此被错误地按《潮流合伙人》的 2.0 分过滤掉、`ヤニねこ` 被按另一部剧的对账结果标成「已删除」，甚至以错误的 TMDB ID 建过订阅）。历史条目现在记录识别策略版本号（`resolve_ver`），版本落后时按当前策略重新识别并回写封面；缓存版本号升至 v3，旧缓存整体作废。

### 升级提示

- 升级后首次同步会重新识别一遍列表中的条目，因此首轮耗时略长（之后恢复正常）。
- 此前若因错配**订阅了错误的影片**（例如以《再见菈菈》的 ID 订阅了《ヤニねこ》），本次修复不会删除已有订阅，请到 dian115 订阅池中核对删除。

## 1.0.3（2026-09-28）

### 修复

- **BangumiTV 等榜单的部分条目无法识别**：这类榜单的标题常是「主标题 + 副标题 + 季号/篇章名」拼成的长串（如 `Re:ゼロから始める異世界生活 4th season 奪還編`、`スティール・ボール・ラン ジョジョの奇妙な冒険 2nd & 3rd STAGE`），TMDB 按整串搜索返回 0 结果。现在整串无结果时会逐级回退到更短的标题候选（`titleCandidates`）：剥掉末尾篇章名（`〜編 / 篇 / 章 / Part / STAGE / Arc`）→ 剥掉季号 → 取主副标题分隔符（`～`/`（`）前的主标题 → 逐词递减。命中后正常识别、显示封面并订阅；日志中会输出 `TMDB 变体命中`（含实际查询词与尝试次数），全部失败则输出 `TMDB 未识别`。
- **TMDB 缓存需要随识别策略失效**：此前「识别失败」的结果也会写入缓存，导致旧条目在新版本里仍被当作未识别而不再重试（改进对存量用户不生效）。缓存的落盘结构现在带 `version`（`tmdbCacheVersion`），版本不符即整体作废并重新识别；旧版本写入的裸 map 不带版本号，同样会被视为过期。缓存命中「未识别」记录时也会输出 `TMDB 缓存命中（未识别）` 便于排查。
- 测试台 mock 的查询参数改用标准 form 解码（此前只做 URI 解码，含空格的查询串中空格仍是 `+`，会影响精确匹配类断言）。

## 1.0.0 — 对外首个正式版本（2026-09-28）

对外发布的首个正式版本。

### 新增

- **想看订阅支持多个豆瓣用户**：`douban_user_id` 支持逗号、中文逗号、顿号、分号、竖线、空格、换行分隔，也可直接粘贴 `douban.com/people/<ID>/` 主页链接（`ParseDoubanUserIDs`）；留空时回退 Cookie 中的 `dbcl2`。逐用户抓取后合并去重，同一部片只订阅一次，单个用户失败不影响其余用户。
- **想看订目标记用户名**：抓取想看页时从 `id="db-usr-profile"` 的封面图解析昵称与头像（回退 `h1`「XX想看的影视(N)」并剥离后缀），缓存到 storage `wish_users`；仪表盘条目显示「想看 · 昵称 等 N 人」（悬浮显示昵称与 ID），想看区块头部按用户汇总，统计卡按用户展示，设置页显示「已识别用户」chips。
- **季号识别**：带季号的标题（如《信号 第二季》《赛博朋克：边缘行者 第二季》）会剥离末尾季号，用基础剧名搜索 TMDB（各季共享缓存），再回填正确 season；季号解析同时支持阿拉伯数字与中文数字（一~九十九）。

### 变更

- **订阅范围改为按榜单位置**：订阅数量只表示「订阅榜单前 N 名」，超出数量的条目状态为 `beyond`（超出订阅数量），不再排队到下一轮补订；榜单 RSS 拉取条数与订阅条数解耦（`rankFetchLimit = max(count, 20)`），保证仪表盘快照始终有足够数据。
- **榜单快照固定显示前 5 名**，移除展开档位。
- 豆瓣用户 ID 输入框提示改为「留空时从 Cookie 自动解析，也可直接粘贴个人主页链接」。
- CookieCloud 文档与占位提示的端口由 `3000` 更正为 `8095`（本机 dian115 内置服务挂在 Web 端口）。

### 修复

- 带季号的电视剧在 TMDB 中按完整标题搜索返回空结果，导致榜单条目无法识别。
- 订阅数量与榜单显示数量相互影响：设置订阅 3 条时榜单只拉到 3 条，且多轮累积会把整个榜单订满。
