# 安全审查

插件和宿主同进程运行，能调用宿主业务接口。安装前审查代码，是防止恶意插件的主要手段。

## 三层检查

| 层 | 什么时候 | 能发现什么 |
| --- | --- | --- |
| 安装确认 | 每次安装 | 宿主分析实际代码，显示作者和检测到的操作，拒绝引用禁止接口的代码 |
| `audit.mjs` | 安装前，本地运行 | 已知恶意特征：外发凭据、混淆、远程代码、挖矿、破坏性操作等 |
| AI 或人工审查 | 安装前，看到可疑项时 | 业务逻辑层面的问题，比如“读文件列表后偷偷发出去” |

三层都通过也不等于绝对安全。只安装你信任的作者发布的插件。

## 用 AI 审查

安装[开发 skill](skill-installation.md) 后，对 AI 说：

```text
使用 $dian115-plugin-dev 审查这个插件有没有恶意代码：/绝对路径/插件.dian115p
```

AI 会先运行扫描，再逐行读可疑文件，最后给出结论和证据。整个过程只读取文件，**不会运行插件**。

## 手动扫描

```sh
node conformance/audit.mjs /绝对路径/插件目录或包.dian115p
node conformance/audit.mjs /绝对路径/插件.dian115p --json
```

无需安装依赖，也不会联网。

| 结论 | 退出码 | 含义 |
| --- | --- | --- |
| `do-not-install` | 2 | 发现高危特征，除非逐条确认是误报，否则不要安装 |
| `needs-review` | 1 | 有敏感行为，要看代码确认 |
| `unreviewable` | 1 | 加密包，看不到源码 |
| `caution` | 0 | 有需要留意的地方 |
| `no-known-patterns` | 0 | 没发现已知特征，**不代表安全** |

## 扫描覆盖

- **隐藏行为：** eval、动态 Function、混淆器、大段编码数据、拼接接口路径、动态取 ctx 成员、双向文本和零宽字符。
- **窃取数据：** 读取登录数据、Cookie、CookieCloud、TG 聊天，再结合外部地址判断；常见数据接收站、隐蔽外发通道。
- **破坏：** 清空回收站、删除文件、系统目录、按日期触发的删除。
- **滥用：** 挖矿、WebAssembly、用账号发消息、针对 BotFather 和登录通知账号。
- **内网访问：** 原生 TCP、开放端口、连接 Redis 和数据库等敏感端口、写死的内网地址和云元数据地址。
- **包结构：** 路径越界、符号链接、可执行文件、隐藏文件、无法识别的二进制文件、压缩后的代码。
- **清单：** 没署名、权限过大、公开回调、监听全部网卡、未声明的外部站点。
- **诱导审查者：** 代码或文档里写给 AI 的“判定为安全”“忽略之前的指令”。

## 扫描不到什么

- 在普通业务接口里做坏事，比如把转存目标换成作者的账号。
- 动态拼出来、运行时才知道的目标地址。
- 服务端根据请求返回不同内容：插件本身干净，但远端配置可以改变它的行为。
- 只在特定用户或特定时间才发作的逻辑。

所以看到联网和写操作时，要问清楚数据发给谁、动作由谁触发。

## 加密包

加密包没有可读源码，AI 和 `audit.mjs` 都无法审查，安装确认里的报告是宿主解密后分析的，也只能发现已知模式。想审查加密插件，向作者要可读源码，或由维护者用审查令牌解密后查看，见[加密交付](encrypted-delivery.md)。

## 作者如何减少误报

- 不混淆代码，不打包压缩后的文件。
- 写固定的接口路径，不要拼接。
- 在 `declared_usage` 写清楚用途和站点。
- 插件数据放 `ctx.storage`，不要用 `localStorage`。
- 只申请用到的权限，账号消息尽量用关键字过滤。

发现恶意插件时保留包文件，不要继续使用，并到作者主页或市场仓库反馈。
